Good to know

  • Lovable connects each project to a GitHub repository it creates. Changes made in Lovable sync to GitHub, and changes pushed to the active branch sync back. The repository can be cloned and worked on in a preferred editor, and paid plans can download the codebase. docs.lovable.dev
  • Supabase's page says a table in an exposed schema without row level security (RLS, rules for who may read or change each row of a table) is readable and writable by any role with a grant on it. Once RLS is on, the API returns no data to a publishable key until policies are created. supabase.com
  • Stripe's page says secret API keys (codes that let software act on a Stripe account) belong in the server environment, never in source code and never embedded in apps. Publishable keys are safe to include in webpages and apps. docs.stripe.com
  • Aibrify's page for Lovable apps lists these problems: a blank screen, sign-in failures, users seeing or changing other users' data, publishing failures, a live app that differs from the preview, data that does not save, tables without row-level security, and server-only keys exposed in the browser. aibrify.com

What people ask

Can someone else fix an app built with Lovable?

Lovable's GitHub page says each project can sync with a GitHub repository. The repository can be cloned and worked on in a preferred editor, and changes pushed to the active branch sync back into Lovable. docs.lovable.dev

Can anyone read a table when row level security is off?

Supabase's page says a table in an exposed schema without RLS is readable and writable by any role with a grant on it. With RLS on, the API returns no data to a publishable key until policies are created. supabase.com

Where does a payment key belong in an app?

Stripe's page says secret API keys belong in the server environment, never in source code and never embedded in apps. It says publishable keys are safe to include in webpages and apps. docs.stripe.com

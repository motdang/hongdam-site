16,326 Supabase databases answer to the public key: check yours in two minutes

ฐานข้อมูล Supabase 16,326 แห่งเปิดให้ใครก็อ่านตารางได้ ตรวจแอปของคุณเองใน 2 นาที

UpGuard counted 16,326 Supabase databases that hand tables to anyone with the public key. A two-minute check on your own project, the SQL that closes it, and what Supabase changes on 30 October.

UpGuard counted 16,326 Supabase databases whose tables answer to anyone holding the app's public key 1. The study, published 24 September 2026 and updated 14 October, started from about 300,000 domains showing signs of Supabase and found indicators of personal data in more than half of the 16,326. UpGuard ties the pattern to how tables get made: Supabase turns row-level security on for tables created in its Table Editor, and tables created through the API, the way coding agents work, do not get it 1.

Row-level security (RLS) is the rule set inside Postgres, the database Supabase runs on, that decides which rows each caller may read or change. Every Supabase app ships a public key in its browser code, called the publishable key (older name: the anon key). Supabase describes it as safe to ship because it only reaches what RLS allows 2. With RLS off, that key reaches every row. A second key, the secret key (older name: the service_role key), skips RLS entirely and belongs on a server 2.

Four scans since March 2025 find open tables at every sample size

Matt Palmer's scan of Lovable projects came first: he found the flaw on 20 March 2025, completed a scan of 1,645 projects on 21 March and published on 29 May 2025 3. NVD, the US vulnerability database, lists it as CVE-2025-48757 (insufficient RLS in Lovable through 15 April 2025): published 30 May 2025, severity 9.3 of 10 as scored by MITRE, the CVE's issuer. The record is marked disputed, because the supplier holds each customer responsible for protecting its own app's data 4.

Wiz found the same state in Moltbook, a social network for AI agents, and reported it on 31 January 2026: the project URL and public key sat in the production JavaScript, RLS was not configured, and queries returned 1.5 million API tokens and 35,000 email addresses. One PATCH request (an HTTP call that edits a record) changed an existing post, so writes were open too. The maintainer closed the tables in rounds within hours 7.

Two requests show whether your own app is open

The Connect dialog in the Supabase dashboard shows the project URL and the publishable key 2. Request one table the app uses, with the placeholders replaced:

curl -s "https://YOUR-REF.supabase.co/rest/v1/orders?select=*&limit=3" \
  -H "apikey: YOUR_PUBLISHABLE_KEY"

Rows in the reply mean every visitor to the site can read that table. [] means the key reaches no rows (RLS on with no policy, or an empty table). A 42501 permission error means the table is not exposed to the key at all 8.

The SQL Editor in the same dashboard checks every table at once:

select c.relname as table_name,
       c.relrowsecurity as rls_on,
       has_table_privilege('anon', c.oid, 'select') as anon_can_read
from pg_class c
join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind in ('r','p')
order by rls_on, table_name;

A row with rls_on false and anon_can_read true is a table the public key reads. Both requests run against your own project.

The fix is RLS on, the public role revoked, and one policy per action

alter table public.orders enable row level security;
revoke all on public.orders from anon;

create policy "owner reads own orders" on public.orders
  for select to authenticated
  using ((select auth.uid()) = user_id);

create policy "owner adds own orders" on public.orders
  for insert to authenticated
  with check ((select auth.uid()) = user_id);

auth.uid() returns the signed-in user's id; wrapping it in select lets Postgres evaluate it once per statement instead of once per row 9.

We ran these statements on 24 October 2026 on a local Postgres (PGlite 0.5.11, Postgres 18.6) with stand-in anon and authenticated roles, not on a hosted Supabase project. Before, the public role read every order. After, the public role got permission denied, user 1 read only user 1's rows, and an insert naming user 2 failed with a row-level security violation.

A policy written true opens the table again

A policy of using (true) matches every row for every caller. Palmer reports that the scanner Lovable shipped in April 2025 checked that a policy exists, not what it says 3. Lovable's documentation now lists rules that let everyone through among its quick scan's database checks, and says the scans find common issues, not all of them 10. On the same local Postgres, a table with a using (true) policy returned its row to the anon role. One query lists the policies that match:

select tablename, policyname, cmd
from pg_policies
where schemaname = 'public' and (qual = 'true' or with_check = 'true');

Supabase changes the default for new tables on 30 October; existing tables keep theirs

A Supabase changelog entry of 28 April 2026 says new tables in the public schema stop reaching the Data API (the generated REST layer that supabase-js calls) until a grant says so. New projects start taking the default from 30 May 2026, in a rollout over a few weeks; the entry schedules every existing project for 30 October 2026, six days after this note. Existing tables keep their grants and stay reachable, and RLS works as before. The entry gives the reason: agents, CLI scripts and AI platforms now create tables without a human reviewing the change 8. The date closes nothing already open; the audit above is the check.

An existing project can adopt the new default today with two statements from the same entry 8. On the local Postgres, a table made afterwards returned permission denied to anon, the older table stayed readable, and an explicit grant select reopened the new one.

alter default privileges for role postgres in schema public
  revoke select, insert, update, delete on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke usage, select on sequences from anon, authenticated, service_role;

An event trigger turns RLS on for every table created afterwards, whichever tool made it. Supabase publishes its own version 11; this shorter one ran in the same test and caught both create table and create table as:

create function rls_on_new_tables() returns event_trigger
language plpgsql security definer set search_path = pg_catalog as $$
declare t record;
begin
  for t in select * from pg_event_trigger_ddl_commands()
           where command_tag in ('CREATE TABLE', 'CREATE TABLE AS', 'SELECT INTO')
             and schema_name = 'public'
  loop
    execute format('alter table %s enable row level security', t.object_identity);
  end loop;
end $$;

create event trigger rls_on_new_tables on ddl_command_end
  when tag in ('CREATE TABLE', 'CREATE TABLE AS', 'SELECT INTO')
  execute function rls_on_new_tables();

Tables created before the trigger need alter table … enable row level security by hand 11.

Two more ways the browser ends up in charge: writable columns and secret keys

On Linkable, a Lovable-built paid site, Palmer sent a POST request with no authorization header and inserted a record with payment_status set to "paid", skipping Stripe 3. A column the browser may write is a column a visitor may set. Column-level grants take the write away: on the local Postgres, a signed-in user's insert or update of plan got permission denied, while display_name stayed writable.

revoke insert, update on public.profiles from authenticated;
grant insert (id, display_name), update (display_name) on public.profiles to authenticated;

The server that receives the payment provider's event then writes plan with the secret key, which skips RLS 2. That key in a browser bundle defeats every policy above. Supabase answers a secret key sent from a browser with a 401 error, and says a leaked key still works from other tools 2. In a framework such as Next.js, a NEXT_PUBLIC_ prefix on a variable name ships its value to the browser:

NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...   # ships to the browser
SUPABASE_SECRET_KEY=sb_secret_...                          # server only: no prefix

grep -r "sb_secret_" dist build .next/static over a build folder finds a new-format secret key left in it. A leaked secret key is replaced in the dashboard under Settings, API Keys 2. Supabase is deprecating the anon and service_role keys by the end of 2026 in favour of the publishable and secret keys 2.
